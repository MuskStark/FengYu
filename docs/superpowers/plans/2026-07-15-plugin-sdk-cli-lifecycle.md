# FengYu Plugin SDK and CLI Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `fengyu plugin` the verified end-to-end path for creating, developing, testing, validating, packaging, and installing Vue + Java plugins, with all official plugins built through the same CLI.

**Architecture:** Keep `manifest.json` as the runtime contract and add optional `fengyu.plugin.json` for build orchestration. The CLI resolves a project model, runs deterministic UI and Maven-wrapper phases, assembles an isolated staging directory, validates runtime contents, and atomically writes `.fyp`; the dev simulator uses the same model to run a real JSON-RPC worker. Official plugins declare the same model and serve as repository-level integration fixtures.

**Tech Stack:** Node.js 20 ESM, Java 21, Maven Wrapper 3.9.11, Vue 3.5, TypeScript 5.9, Vite 7, Vitest 3, JUnit 5, JSON-RPC 2.0, npm registry, GitHub Packages Maven.

## Global Constraints

- `manifest.json` remains runtime-only; build commands and source paths belong only in `fengyu.plugin.json`.
- Default `fengyu plugin create` generates Vue + Java; `--ui-only` preserves the lightweight scaffold.
- Existing zero-config Vite and static plugins must continue to build without `fengyu.plugin.json`.
- All configured path fields must resolve inside the plugin root; reject absolute paths, `..` escapes, and symlink escapes.
- Configured commands are argument arrays passed without shell concatenation.
- The logical command `maven` must resolve `mvnw` or `mvnw.cmd`; never silently fall back to system Maven.
- `build` runs UI and worker tests by default; `--skip-tests` skips tests only, never type checking or packaging.
- `.fyp` output must be staged, validated, and atomically renamed; failures leave no partial package or staging directory.
- Java SDK and the three npm packages share plugin-tooling version `1.0.0` for this implementation.
- Java SDK consumers authenticate to GitHub Packages through `FENGYU_GITHUB_TOKEN` or `GITHUB_TOKEN`; generated files never contain a token.
- Official Markdown, Excel, and Email packages must be produced only by `fengyu plugin build`.
- Preserve unrelated worktree changes; every task stages only its listed files.

- [ ] **Step 4: Centralize TypeScript pending cleanup**

Change `Pending` and add a cleanup helper:

```ts
type Pending = {
  resolve(value: unknown): void
  reject(error: Error): void
  timer: ReturnType<typeof setTimeout>
  signal?: AbortSignal
  abort?: () => void
}

private takePending(id: string): Pending | undefined {
  const item = this.pending.get(id)
  if (!item) return undefined
  this.pending.delete(id)
  clearTimeout(item.timer)
  if (item.signal && item.abort) item.signal.removeEventListener('abort', item.abort)
  return item
}
```

Use `takePending` in timeout, abort, response, and `dispose` paths.

```js
export function validateManifestObject(manifest) {
  const errors = []
  if (!validateSchema(manifest)) {
    errors.push(...validateSchema.errors.map(e => `manifest${e.instancePath}: ${e.message}`))
  }
  const names = new Set(), methods = new Set()
  for (const tool of manifest.aiTools ?? []) {
    if (names.has(tool.name)) errors.push(`duplicate AI tool name: ${tool.name}`)
    if (methods.has(tool.method)) errors.push(`duplicate AI tool method: ${tool.method}`)
    names.add(tool.name); methods.add(tool.method)
    try {
      const schema = JSON.parse(tool.inputSchema)
      if (schema?.type !== 'object') errors.push(`inputSchema for ${tool.name} must have type object`)
    } catch {
      errors.push(`invalid inputSchema for ${tool.name}`)
    }
  }
  return errors
}
```

# Infinia 4.0 路线图

本路线图优先交付可靠的 4.0 版本，而不是继续扩大功能面。目标时间窗用于推动收敛，但只有满足退出标准后才能晋级下一阶段。

## 当前决策

**在首个 RC 之前先发布 `v4.0.0-beta.5`。** 当前变更范围不适合直接进入 RC：其中同时包含 Flow
编辑与恢复、代码优先插件契约、智能体/工具加载、桌面更新、UOS 打包和文档更新。Plugin
Toolchain 2.1.0 也已经出现在源码和文档中，但远端尚无对应发布标签。

截至 2026-08-24 的快照：

- 当前工作树相对 `v4.0.0-beta.4` 涉及 522 个文件，约新增 31,900 行、删除 8,900 行；
- 工作树仍包含已跟踪和未跟踪改动，尚不能打标签；
- 后端、前端、桌面、CLI、Java SDK/DevKit、Go SDK 和文档的重点检查已通过；
- 完整发布装配、宿主冒烟、Web 压缩包自检、Python SDK 测试和完整跨平台发布矩阵仍需最终证据。

## 发布列车

| 目标时间窗 | 里程碑 | 变更策略 | 退出结果 |
|---|---|---|---|
| 2026-08-24 至 2026-08-28 | 范围冻结与 `v4.0.0-beta.5` | 只完成已确认属于 4.0 范围的工作 | 一个完整的、承载最终功能的 Beta |
| 2026-08-29 至 2026-09-03 | Beta 稳定期 | 仅 P0/P1 修复，以及低风险测试和文档 | 无已知发布阻塞回归 |
| 目标 2026-09-04 | `v4.0.0-rc.1` | 不新增功能、公开契约或迁移 | 用于最终验证、形态等同 GA 的构建 |
| 2026-09-05 至 2026-09-10 | RC 观察期 | 仅阻塞修复；功能修复可能要求新增 RC | 所有分发和升级路径验收通过 |
| 目标 2026-09-11 | `v4.0.0` | 只允许版本和发布文档变更 | 正式发布 |
| GA 之后 | `4.0.x` 稳定期 | 仅向后兼容的修复 | 稳定维护线 |

如果门禁未能在目标时间窗内通过，应移动里程碑，而不是降低门禁。

## 阶段一——冻结并发布 beta.5

### 纳入范围

- 无头 Spring Boot 后端、首次启动设置、仅环回地址的 Web 运行时和 Electron 桌面外壳。
- 可视化流程：类型化节点、IF 与 LLM 节点、单步调试、输入/输出绑定、本地草稿恢复、重启检查点和持久化执行遥测。
- 智能体运行时：动态工具加载、MCP 控制、后台任务调度、审批和持久化通知。
- 插件平台：schema v2、代码优先的 Java/Python/Go 契约、生成的清单和客户端、沙箱 Worker，以及四个官方插件。
- 分发：便携 Web 包、Windows/macOS/Linux 桌面变体、UOS 包、校验和、更新器行为和发布文档。

### 必须完成

1. 停止接收新的 4.0 功能，并确认唯一的发布提交/分支。
2. 明确处理所有已跟踪删除和未跟踪源码；只能从干净工作树打标签。
3. 在文档声称插件作者可使用 2.1.0 前，通过独立发布线发布 Plugin Toolchain `2.1.0`；不得把工具链版本与应用版本绑定。
4. 将当前 `Unreleased` 更新日志折叠为 `4.0.0-beta.5`，并同步所有应用版本镜像。
5. 完成下方发布验证矩阵，并实际运行生成的 beta.5 制品。

### beta.5 退出标准

- 无 P0 缺陷；不存在未经过明确阻塞决策的已知 P1 缺陷。
- 全新安装和从 beta.4 升级均保留设置、流程、插件状态和数据库迁移结果。
- 四个官方插件的安装、更新、调用、重启和卸载全部通过。
- Windows 便携版在曾经打开插件 Worker 的情况下仍可成功完成更新。
- GitHub 发布工作流产出所有预期制品及校验和伴随文件。

## 阶段二——稳定 beta.5

把 beta.5 当作兼容性和打包彩排。必须测试真实发布制品，不能只测试开发服务器或本地组装的 JAR。

必测场景：

- 使用 H2/SQLite 全新设置，并至少覆盖一条外部数据库路径；
- beta.4 至 beta.5 应用升级，包括 Windows 便携版路径；
- Flow 创建、草稿恢复、执行、重启恢复、重试/跳过遥测和已发布流程调用；
- Java、Python、Go Worker 的插件包校验与完整生命周期；
- Windows、Apple Silicon macOS、Linux、UOS 上的 Web 包和桌面启动；
- 离线或内网更新失败时提供可操作日志，并保持安装可恢复。

本阶段只接收 P0/P1 修复。P2 只有在改动局部、具备回归测试，并且不改变公开契约或持久化格式时才可进入。

## 阶段三——候选发布版

RC1 表示 4.0 已经功能完整、契约完整，不是另一个 Beta。

### RC1 进入标准

- beta.5 已完成稳定期场景，且没有未关闭的 P0/P1 缺陷；
- Plugin Toolchain 2.1.0 已发布，全新生成的插件能够完成 `init`、`dev`、`check`、`build`、安装和调用；
- 不再存在待完成的 schema、REST/SSE、数据库迁移、更新器或打包变更；
- beta.5 到 RC 的差异仅包含修复、测试、文档和发布元数据；
- 所有应用版本镜像均解析为 `4.0.0-rc.1`，发布工作流契约测试通过。

### RC 观察规则

如果 RC 验证需要修改功能代码，应发布 `rc.2`。只有当 GA 仅需调整发布元数据和文档、无需改变二进制行为时，才能直接从 RC1 晋级 GA。

## 阶段四——正式发布

GA 要求：

- 完整 Windows/macOS/Linux 发布矩阵和 Linux 宿主冒烟测试全绿；
- 便携 Web ZIP 和 tarball 自检通过；
- JAR、桌面、UOS、`.fyp`、校验和与更新器元数据制品齐全；
- 发布说明明确桌面包尚未签名，并准确说明完整性校验；
- 安装、升级、回滚/恢复和故障排查文档与实际制品一致；
- 未关闭 P0/P1 数量为零。

## 发布验证矩阵

| 表面 | 必须通过的门禁 |
|---|---|
| 后端 | 完整 Maven reactor 测试/打包，以及 `scripts/e2e-smoke.sh` |
| 前端 | immutable 安装、生产依赖审计、构建、单元测试、Node 测试和类型检查 |
| 桌面 | 生产依赖审计、单元测试、TypeScript 构建，以及 Linux/macOS 的阻塞式启动 E2E |
| 插件平台 | CLI/spec 测试、Java/Python/Go SDK 测试、DevKit 测试和四个官方 `.fyp` 构建 |
| Web 分发 | `package-web-release.sh` 后运行 `test-web-release.sh` |
| 文档 | 中英文结构一致、生成式更新日志同步和 VitePress 构建 |
| 发布工作流 | 版本/工作流契约测试，以及完整制品/校验和检查 |

## beta.5 之后的缺陷策略

| 级别 | 定义 | 发布处理 |
|---|---|---|
| P0 | 安全暴露、数据丢失、更新损坏或应用无法启动 | 阻塞所有里程碑 |
| P1 | 核心 Agent/Flow/插件生命周期不可用，或受支持平台无法安装/更新 | 阻塞 RC 和 GA |
| P2 | 存在可行规避方式的局部功能或体验缺陷 | 除非修复隔离且测试完整，否则推迟 |
| P3 | 打磨、优化或功能请求 | 移入 4.0 之后的待办 |

## 明确推迟到 4.0 之后

- 新的官方插件或新的 Flow 节点家族；
- 另一套插件清单/schema 生成模型；
- 新增 AI 服务商或新的工具加载架构；
- 局域网/公网绑定、多用户协作或远程服务器部署；
- 再次重做外壳或导航；
- 当前 4.0 发布线尚未配置的桌面代码签名/公证工作。

首次 GA 后规划检查点应先观察 4.0.x 的现场数据，确认启动、更新、Flow 执行和插件生命周期稳定，再为 4.1 排定这些事项。

## 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| beta.4 到当前版本差异过大 | 先发 beta.5，并在 RC 前进行真实制品观察 |
| Toolchain 2.1.0 源码/文档存在但没有对应发布 | 先独立发布工具链，或撤回可用性声明 |
| 长期存在且未清理的功能分支 | 选择唯一干净的发布提交，禁止从脏工作树打标签 |
| 跨平台行为不一致 | 以发布工作流矩阵和桌面启动 E2E 作为证据源 |
| Windows 更新器遗留插件子孙进程 | 打开插件后执行更新，并检查更新器日志 |
| 生成清单、文档或锁文件漂移 | 保持生成、immutable 安装、spec 同步和发布契约检查为阻塞门禁 |
